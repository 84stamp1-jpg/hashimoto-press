### 1. 段取りナビ / H-Hubポータル(dantori_navi.html)
- **目的**: 金型段取り時間の短縮。品番検索→標準作業表示、BLEビーコンによる位置追跡
- **兼務**: `<title>` は「H-Hub」。HHubポータル本体を兼ね、2026-06-03に進捗管理タブを統合済み
- **構成**: BLEビーコン(MM-BLEBC5)+ 常時稼働PC(Node.jsスキャナー)→ Firebase → HTML表示。
  品番マスタは kintone App7
- **表示**: 工場レイアウトSVG v11(viewBox="0 0 824 446")
- **設置**: GitHub Pages 単体 + kintoneポータル埋め込み(kintone.api()直接呼び出し版)
- **既知の課題**: ビーコンアイコンの「ac」表示問題(MACアドレスプレフィックス由来)、
  一部PCでPDF直接表示不可(JSONP方式で対応)
- **セキュリティ対応(2026-07-07)**: HTMLにハードコードされていたkintone App7のAPIトークンを除去。
  トークンが必要な機能は設定画面から端末ごとに入力(localStorage保存)。
  旧トークンはkintone側で失効・再発行済み。新トークンはGASプロキシ(段取ナビ)側に設定
- **GAS URL修正(2026-07-07)**: FIXED_CONFIGのgasUrlが品質チェックUIのデプロイ(JSONP非対応)を
  指していたため、kintoneレコードJSONPプロキシ(旧proxyUrlと同一)に修正。
  品質チェックシートを開く処理はqualityGasUrlを使用するよう変更。
  旧gasUrlを保存済みの端末はリロード時に自動移行
- **予定インポートの実績消失バグ修正(2026-08-24, v2026.08.24-1)**: 「実績・稼働状況を維持して
  インポート」にチェックしても実績が消える事象。原因は `lines/<id>/jobs` 配列を丸ごと差し替えて
  いたこと。ライン単位の `actual/status/workStart/workEnd` は維持されるが、**品番ごとの実績は
  jobs要素内**(`actualCount`/`actualStart`/`actualEnd`/`status`)にあるため全て初期化されていた。
  「消える時と消えない時がある」のではなく、**完了済み品番があると必ず消える**。
  さらに稼働中ジョブの特定が `j.actualStart===l.workStart` の一致で行われるため、
  actualStartが空になると現在ジョブを見失い、残っていたライン実績も表示上ぶら下がらなくなる。
  修正: `_mergeActualIntoJobs()` を追加し、既存jobsから**品番(trim比較)で照合して実績を引き継ぐ**
  (同一品番が複数ある分割生産は出現順に1件ずつ引き当て)。新計画に無い品番の実績は引き継げないため、
  確認ダイアログで**品番名を挙げて警告**する。`part` も稼働中品番が新計画に残っていればそれを維持。
  ※ 別ツール `upload_tool_v2.html` の keepActual も同じ構造のため要確認
- **進捗ボードの実績消失(その2)・並行生産の巻き込み完了を修正(2026-08-26, v2026.08.26-1)**:
  (1)**「計画修正(実績を維持したまま変更)」パネル**が実績を `actual` という**存在しないフィールド名**で
  参照していた(正しくは `actualCount`)。影響は3つ ── 実績バッジが常に「未実施」表示／行削除時の
  「実績も失われます」警告が出ない／**保存後に `_peAllLines` を一部フィールドだけで作り直すため
  actualCount・status・kata・ninzu・hito・seq が欠落し、パネルを開いたまま2回目に保存すると実績が
  ゼロで書き込まれる**。「インポート直後は残っていたのに、いつの間にか消えた」の正体はここ。
  修正: `_jobActualCount()`/`_jobHasActualData()` を追加(旧データの `actual` も互換で参照)、
  保存後キャッシュは `{...oj}` に編集値だけ上書きする方式へ変更し、行の `data-origji` も貼り直す。
  `apPushToProgress` の hasActual 判定も同様に修正。
  (2)**並行生産・同名品番での巻き込み完了**。原因は `lines/<id>` が `part/workStart/workEnd/actual`
  を**1組しか持たない**設計で、現在稼働行を**品番一致**(`j.part===l.part`)で探していたこと。
  同名品番が2行あると必ず先頭がヒットし、`jobDone` の
  `l.workEnd!=='' && l.part===j.part` により別行が完了扱いになっていた。
  修正: **`lines/<id>/curSeq`(行番号seq)を正**とし `curJobIndex()` 1か所で判定。`jobDone` から
  ライン単位の条件を削除(行自身の status/actualEnd のみ)。実績入力のライン同期は
  `selJi===curJi` のときだけ。「次品番へ切替」も稼働行本人が終了した時のみ＆**未完了の次行**へ送る。
  計画差し替え時は `remapCurSeq()` で稼働行のseqを貼り直す(インポート/計画修正の両方)。
  旧データは curSeq 無しでも従来ロジックで推定するため移行不要。
  ※ブラウザ上で22項目の検証を実施(同名品番/並行生産/計画入替/実績引き継ぎ/実績判定)し全通過
- **品質チェックタブ 3点改修(2026-09-05, v2026.09.05-1)**:
  (1)**表示が遅い**。記録一覧(`getRecords`)はGASの往復に数秒かかるのに、タブ初期化・日別一覧・
  製造番号検索がそれぞれ別々にリクエストしており(同じ通信が2〜3本重なる)、返るまで画面を
  「読み込み中...」で空にしていた。そのためバッジを押すまで何も出ないように見えていた。
  `qcAllRecordsCache`(localStorage)は**書くだけで読んでいなかった**ので実際に読むようにし、
  手元のデータを先に描画→裏で最新に差し替える方式へ変更。`qcFetchRecords()` で多重リクエストを
  1本にまとめ、待っているコールバックへまとめて返す。
  (2)**製造番号・部品番号のワンタップコピー**(`qcCopyChip`)。行ごと選択すると「製造番号: 」まで
  入ってしまい、社内システムへ貼るときに直す手間があった。番号だけをクリップボードへ入れる。
  clipboard APIが使えない環境向けに textarea+execCommand のフォールバックあり。
  (3)**システム入力待ちの右にkintone「★不良品報告」(App31)を並べて照合**(`qcNg*`)。
  記録した不良が報告に挙がっているかを画面を行き来せずに確かめる。品番で突き合わせ、
  不良の記録があるのに報告が無い場合は赤で警告、報告があれば「kintoneで開く」で
  `/k/<app>/show#record=<$id>` へ直行。中継は品質チェックGASの汎用アクション
  `getKintonePartData`(domain/appId/token/query/fields を受ける)を流用しており**GASの変更は不要**。
  ※**`LOGINUSER()` はAPIトークンでは効かない**(トークンに利用者がいない)ため、kintone側の
  「作業者が自分」ビューの条件は使わず、直近レコード(`order by $id desc limit N`)を取って
  クライアント側で品番照合する。品番は全角→半角・空白除去・ハイフン統一で正規化し、
  完全一致を優先、部分一致は「参考表示」と明示する。
  トークンとフィールドコードは「⚙ 不良品報告の設定」から端末ごとに登録(`qcNgReportCfg`/
  localStorageのみ・**リポジトリには入れない**)。フィールドコードは「🧾 列を確認」で
  1レコード取得して一覧表示＋自動推測。この画面だけ `.qc-cont` の幅上限500pxを外す(`.qc-wide`)。
  1000px以下では縦積み。
- **不良品報告ペインを実用形に(2026-09-05, v2026.09.05-2)**:
  (1)**記録カードを元の幅(476px)へ戻した**。前版はカードを986pxまで広げたため中央に余白ができて

  (3)1品番に報告が複数あるのが普通なので**全件表示**(件数も出す)。
  (4)**不具合数量・廃棄数量・合格数量の三点**を表示。不具合数量と廃棄数量は「不具合一覧」

  (6)**「▶在庫調整」「▶在庫投入」でプロセス管理を進める**。在庫投入は**合格数量>0のときだけ**押せる。
  書き込みは毎回 `confirm` で内容(品番・三点の数量・書く値／アクション名と現ステータス)を

- **書き込みは「別GAS」へ分離(2026-09-05, v2026.09.05-3)**:
  当初は品質チェックGASに `kintoneWrite` を足す前提だったが、**あのGASは記録の保存・読み込みに
  毎日使っており、直し損ねると品質チェックそのものが止まる**。書き込み専用のGASを1つ立てて
  そちらへ投げる形に変更した。`qcGasPost` を `qcGasPostTo(url, ...)` に分離し、
  `qcNgWriteUrl()` が書き込み先を返す。
  - **ヘッダーは付けない**こと。`Content-Type` を付けるとプリフライト(OPTIONS)が飛び、
    GASはそれに応えないためCORSで落ちる
  - 「⚙ 不良品報告の設定」に**「書き込み用GASのURL」**と**「🔌 接続テスト」**(action:'ping')を追加。
    未登録でも**照合（読み取り）は今までどおり動き**、書き込みボタンを押したときだけ理由を出して止まる
  - GASコード全文（doPost込み・そのまま貼るだけ）: `docs/kintone_write_gas.gs.example`
    （`ALLOWED_APPS` で書き込み先アプリIDを31に限定。トークンはGASに保存せずH-Hubから毎回渡す）
  - 作成手順（クリック単位）: `docs/kintone_write_gas_setup.md`
  - トークンは**レコード編集**（プロセスを進めるなら**ステータス変更**も）の権限が要る。
    kintoneでアクセス権を足したあと**「アプリを更新」を押し忘れない**こと
- **明細表示・並び順・接続テストの見え方(2026-09-05, v2026.09.05-4)**:
  (1)**「🔌 接続テスト」が無反応に見えた**。ボタンは動いていたが、結果をモーダル下端の共通
  メッセージ欄(`#qc-ng-cfg-msg`)に出しており、フィールドが並ぶ長いモーダルでは**画面外**だった。
  ボタンの真横(`#qc-ng-wgas-msg`)に出すよう変更。
  ※**結果を離れた場所に出すと「押しても何も起きない」と受け取られる**。DOMの確認だけでは
  気づけないので、この種のボタンは押した位置の近くに返すこと
  (2)同じレコードの中の不具合数量・廃棄数量を、合計だけでなく**明細で一覧表示**。
  `qcNgSubRows()` がサブテーブルの各行から数量と、同じ行の他の列（不具合内容・廃棄内容）を
  取り出す。合計と✓による三点確認はそのまま残している
  (3)並び順を**不具合発生日の古い順**に（日付なしはその組の最後）。
  品番が完全一致でないもの（参考表示）は、日付に関わらず**常に下**にまとめる

  - **凹(伸び)は詰める余地があるが、凸(縮み)は逃がす**。凹の穴(閉じた円)は全周拘束されるため
    しごき(0.65〜0.75ta)が成立するが、開いた縁・凸側で ta を下回らせると割れ・しわ噛みになる
- **用語統一(2026-08-22)**: バーリングと対になる加工の呼称を **「フランジダウン」→「縁曲げ」** に
  全廃・統一(3編Excel＋クリアランス基準書)。共通編 C5-3 は「縁曲げ(フランジベンド)の狙い値」、
  C5-4 は「バーリング/縁曲げの前工程の面の位置」に改称。
  **`FL-DOWN` は置換しない**(HMS設計値管理表.xlsx の記録シート名 `02_FL-DOWN` の識別子のため)
  - シート名変更に伴い `build_hms_docs.py` の `CLEAR_SHEETS` と、両ビルダーの5-補 早見表の
    シート指定・説明文を更新。共通編 C5-2/C5-3 の規定内容と 00_はじめに にも参照を追記
- **ステンレスの基準材を変更(2026-08-22)**: 基準書3シート(ピアス・抜き/フランジ成形/曲げ)の
  「ステン」列を **SUS304 → HFS436L・HFS429M(フェライト系)** に変更。当社の使用実績が
  436L 最多・次いで 429M/409L で、SUS304 は少数のため。SUS304 の値は各シートの注記に残した。
  根拠はJFEスチール自動車用ステンレス鋼カタログの代表値(板厚0.8mm):
  SUS436L=引張482MPa/伸び31%/n値0.25/r値1.4/穴拡げ率37.5%、
  SUS304=引張652MPa/伸び57%/n値0.34/r値1.0/穴拡げ率38.4%。
  → 加工硬化とスプリングバックは304より小さく軟鋼に近い／伸びが小さく高フランジ・急な曲げは
  304ほど利かない／穴拡げ率は同等なのでバーリング自体は成立する、という整理。
  **⚠️ 曲げシートの最小曲げ内R(1.0〜2.5t)とスプリングバック(2〜4°)は材料特性からの暫定値**。

### 18. 現場⇔事務所インターコム(検討中)
- **目的**: 事務所から現場への呼びかけと双方向の対話。同一社内WiFi環境で**配線工事なし**で実現する
- **前提・制約(2026-08-25 確定)**:
  - **工事不要が条件** → ホーンスピーカーによるIP構内放送は不採用
  - **手ぶら(ハンズフリー)が必須**。現場は油が付き両手がふさがるため、端末を持ち歩くPTT方式は次善
  - **騒音下では音より光が届く**。プレス稼働中は通常のスピーカー音声は届かない前提で設計する
- **方針: Amazon Echo Show を2台で試行 → 結果を見て拡張**
  - **ドロップイン(Drop In)は受け手の操作なしで音声がつながる**ため、手ぶら要件を満たす唯一の市販品
  - アナウンス(一斉呼びかけ)とドロップイン(1対1対話)が1台で両方できる
  - 接続時に画面が点くので「光で気づく」を兼ねる → Echo Dot ではなく **Show** を選定
  - 設置: **事務所×1 / 技術部×1**。技術部は MILLAC と MX55 の中間・目に入る高さ
    (機械の真横は切粉・油がかかるため避ける)。物理条件はコンセントのみ
  - **技術部はプレスより静かなため、ここで成功してもプレスラインで通用する保証はない**。段階検証する
- **⚠️ 導入前の必須事項**:
  - **Amazonアカウントは会社名義で新規作成**する。個人名義は引き継ぎ書§2の「個人アカウントは
    本人以外が触れない」問題を1つ増やす。**後から直せないため最初にやること**
  - **3.5mm音声出力の有無は機種・世代で異なる**(新しい世代で廃止)。将来プレスラインで外部
    スピーカーを足す際に必要になるため、購入前に型番で確認する
  - **ドロップインは相手の同意なくつながる**。用途を事務所⇔技術部の業務連絡に限定し、許可相手を
    この2台間だけに絞る。休憩スペースには置かない。**双方向であることを技術Tへ事前説明する**
    (「事務所から一方的に聞ける装置」と受け取られると労務面のトラブルになる)
- **検証項目(合否の目安)**: ①事務所→技術部の呼びかけがMILLAC稼働中に気づけるか
  ②**技術部→事務所の声を拾えるか(最大の不確実要素。机上では判断不能)**
  ③画面点灯に作業中でも気づくか ④遅延1秒以内で会話が成立するか ⑤機械音でウェイクワードが誤反応しないか
- **②がNGの場合**: 「呼びかけ専用」に格下げし、対話は電話または直接。あわせて下記の自作案へ切り替える
- **代替案(自作・追加費用ゼロ)**: カメラ仕様書 Phase3「トラブルボタン」の**逆方向**。
  事務所でHHubの工場レイアウトから相手/エリアを選び「呼び出し」→ Firebase `/call/<エリア>` →
  現場タブレットの段取りナビが全画面赤点滅＋チャイム → 「了解」で解除。
  **BLEビーコンで対象者の現在エリアが分かるため、そのエリアだけ光らせられる**(当社固有の強み)
- **不採用にした案**: SIP/VoIP(FreePBX＋IPインターホン)=構成が複雑で属人化し引き継ぎ書の方針に反する /
  Slackハドル=能動的に参加しないと繋がらず呼び出しに不向き / Echo Dot=画面がなく光で気づけない /
  Tapo C210の双方向通話=音量不足・クラウド遅延(ただし**0円で音量の壁を実測できる**ため事前テストには有用)
